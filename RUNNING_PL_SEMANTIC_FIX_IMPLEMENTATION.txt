1. PROBLEM STATEMENT
================================================================================

CRITICAL ISSUE IDENTIFIED:
The Running P&L chart was displaying RED area fill when the account was 
PROFITABLE (P&L positive). This created a dangerous semantic contradiction:
- User sees green profit line (P&L: +$171.50)
- User sees red area fill beneath the line
- User's brain interprets red as "loss" (semantic failure)
- Result: Chart communicates WRONG meaning for trading journal

ROOT CAUSE ANALYSIS:
The original implementation used a single <Area> component with SVG gradient fill.
By default, Recharts Area components anchor their fill to the BOTTOM of the chart,
not to the Y=0 (breakeven) line. This meant:
- Gradient filled from bottom to line
- Color semantics were determined by the gradient, not by the data domain
- Red gradient coloring the bottom-anchored area created visual inversion
- No amount of gradient tweaking could fix the fundamental architectural problem

PREVIOUS ATTEMPTED FIXES:
1. Dynamic gradient with zeroLineOffset calculation (FAILED)
   - Still used single Area component with bottom-anchor
   - Gradient coloring couldn't override semantic meaning of data domain
   - Semantic problem persisted despite visual adjustments

SOLUTION CHOSEN: Option A - Split Area Series Architecture
- Replace single Area with two separate Area components
- Each area is anchored at Y=0 (baseLine={0}) using Recharts baseLine property
- Positive data (balance >= 0) → Green area (profit semantics)
- Negative data (balance <= 0) → Red area (loss semantics)
- Separate Line component for equity curve (dominates visually)
- Result: Semantic meaning preserved, no color bleeding across zero line

CHANGE #1: Data Split Logic (Lines 156-180)
────────────────────────────────────────────

Added useMemo hook to split enhancedData into two series:

  const { positiveData, negativeData } = useMemo(() => {
    if (!enhancedData || enhancedData.length === 0) {
      return { positiveData: [], negativeData: [] };
    }

    // Split data at the zero line for semantic correctness
    const positive: EnhancedDataPoint[] = [];
    const negative: EnhancedDataPoint[] = [];

    enhancedData.forEach((point) => {
      if (point.balance >= 0) {
        positive.push(point);
      }
      if (point.balance <= 0) {
        negative.push(point);
      }
    });

    return { positiveData, negativeData };
  }, [enhancedData]);

PURPOSE:
- Separates the equity curve into two domain-specific series
- Point at exactly 0 is included in BOTH series (ensures no gaps at breakeven)
- Ensures green fill area ONLY contains data where balance >= 0
- Ensures red fill area ONLY contains data where balance <= 0
- Eliminates possibility of color bleeding across zero boundary

4. TECHNICAL ARCHITECTURE
================================================================================

COMPONENT HIERARCHY:
ComposedChart (container)
├─ XAxis (dates)
├─ YAxis (P&L values in $)
├─ CartesianGrid (optional)
├─ Tooltip (custom)
├─ Legend
├─ Area (Profit Zone)      ← baseLine={0}, positiveData only
├─ Area (Loss Zone)        ← baseLine={0}, negativeData only
├─ Line (Equity Curve)     ← enhancedData, dominates visually
└─ ReferenceLine (y=0)     ← visual breakeven marker

DATA FLOW:
trades[] 
  → cumulative sum 
  → enhancedData[] (with cumSum, date formatting, etc.)
  → split at y=0 
  → positiveData[] + negativeData[]
  → render two Area components + one Line component
  → semantic correctness preserved

BASELINE PROPERTY EXPLANATION:
The baseLine={0} property is the KEY FIX:
- Without baseLine: Area fills from data to CHART BOTTOM (semantic problem)
- With baseLine={0}: Area fills from data to Y=0 (semantic correctness)
- This ensures fill only occupies the correct profit or loss domain
- Two separate areas with baseLine={0} create hard regime boundaries

7. KEY LEARNINGS
================================================================================

PRINCIPLE 1: Semantic Correctness > Visual Polish
- A chart that "looks better" but communicates wrong meaning is dangerous
- In financial software, color semantics are non-negotiable
- Fix the architecture, not just the appearance

PRINCIPLE 2: Use the Right Data Structure
- Single data series with gradient = semantic inversion risk
- Split data series by domain = semantic guarantee
- Let data structure enforce business logic

PRINCIPLE 3: Anchor Points Matter
- baseLine property controls where fills anchor
- Default behavior (bottom-anchor) often wrong for financial charts
- Explicit baseLine={0} for correct regime separation

PRINCIPLE 4: Visual Hierarchy Through Layering
- Area components = subtle fills (secondary information)
- Line component = dominant stroke (primary information)
- Component order in JSX controls Z-order (render order)
